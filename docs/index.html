#01. Project Overview & Introduction

#What is MelLang?

MelLang is a dynamically typed, purely functional programming language implemented as a tree-walking interpreter in F# (.NET 8). Developed as an academic coursework project, it serves as a rigorous demonstration of core functional programming concepts, interpreter architecture, and language design principles.

#Design Philosophy

The language deliberately decouples lexical surface from operational semantics. All standard programming constructs are mapped to phonetic transcriptions of viral internet culture phrases (specifically, those associated with Russian streamer Andrey "Mellstroy" Burim). This is not a stylistic gimmick, but a pedagogical design choice: it demonstrates that language keywords are arbitrary tokens bound to fixed computational rules, proving that syntax is entirely independent of semantics. The underlying execution model adheres strictly to academic standards for functional interpreters.

#Core Paradigm & Execution Model

MelLang operates on a strict functional paradigm with the following architectural guarantees:

  • Tree-Walking Evaluation: Programs are executed by recursively traversing an Abstract Syntax Tree (AST). No bytecode compilation, JIT, or intermediate representation is generated.
  • Persistent Lexical Environments: State is managed through immutable Map<string, Value> structures. Every binding creates a new environment scope, ensuring referential transparency and eliminating mutable global state.
  • Explicit Scoping & Closures: Functions capture their defining environment at creation time, enabling correct lexical scoping and first-class function behavior.
  • Controlled Side Effects: The language is pure by design. I/O and console output are strictly isolated to the Print construct, preserving functional composition elsewhere.

#Key Capabilities

Feature Description
First-Class Functions Functions are values that can be passed, returned, and stored. Full closure support is implemented.
Higher-Order Operations Built-in map, filter, fold, and a functional pipeline operator enable declarative data transformation.
Lazy Evaluation Explicit let-lazy bindings wrap expressions in memoized thunks (System.Lazy<T>), guaranteeing at-most-once evaluation upon first force.
Recursive Bindings Native support for recursive function definitions via self-referential environment injection.
Uniform S-Expression Syntax All code is expressed as nested parenthetical lists, simplifying parsing and eliminating operator precedence ambiguity.
Dynamic Typing Types are resolved at runtime. The interpreter enforces strict value contracts during built-in function application.

#Target Audience & Academic Context

MelLang is intended for:

  • Students studying functional programming paradigms and language implementation.
  • Developers exploring interpreter design patterns (explicit environment passing, thunk-based lazy evaluation, AST traversal).
  • Researchers or educators demonstrating the decoupling of lexical syntax from semantic execution.

The project prioritizes clarity of implementation over runtime performance. It is designed for educational analysis, coursework submission, and language experimentation, not for production workloads or large-scale deployment.

#02. Getting Started & Environment Setup

This guide walks you through installing the necessary dependencies, building the interpreter, and executing your first MelLang program. It assumes a standard development environment with command-line access.

#System Requirements

  • .NET 8 SDK: Required for compilation and runtime execution. The project targets net8.0 but supports roll-forward to newer .NET versions.
  • Operating System: Linux, macOS, or Windows (cross-platform via .NET Core runtime).
  • Terminal/Shell: Bash, PowerShell, Zsh, or any POSIX-compatible CLI.

#Installation & Build

  1. Clone the Repository:

    git clone <repository-url>
cd funcpro-coursework-prikolno-2/MelLang

  2. Verify .NET Installation:

    dotnet --version

    Ensure the output indicates version 8.0.x or higher.

  3. Restore Dependencies & Build: The project uses standard .NET MSBuild tooling. Dependencies are resolved automatically, but an explicit build guarantees a clean state: 

    dotnet restore
dotnet build --configuration Release

    (No external package managers, Docker containers, or IDEs are strictly required. Development is fully supported via CLI, though VS Code + Ionide F# or JetBrains Rider is recommended for larger modifications.)

#Running Programs

MelLang is executed via the dotnet CLI. You must pass the .mel source file as a positional argument.

⚠️ Critical Syntax Note: The -- separator is mandatory. It instructs the dotnet CLI to forward all subsequent arguments to the compiled application rather than interpreting them as CLI flags. 

dotnet run -- <path-to-source.mel>

#CLI Behavior & Exit Codes

The interpreter (Program.fs) implements strict error routing:

Exit Code State Description
0 Success Program parsed and evaluated without fatal errors. Output printed to stdout.
1 Failure Error encountered. Message prefixed with Error: is printed to stderr.

Common failure triggers:

  • Incorrect argument count (must provide exactly one file path)
  • Target file does not exist
  • Lexical/Syntactic parsing failures (unbalanced parentheses, malformed tokens)
  • Runtime evaluation errors (type mismatches, unknown variables, division by zero)

#03. Syntax Reference & Lexical Specification

#1. Lexical Structure

The lexical analysis phase is implemented as a single-pass, index-driven character scanner (tokenize in Parser.fs). It operates strictly on raw source text, consuming characters and emitting a linear stream of string tokens. Whitespace and syntactic delimiters are resolved during this stage; no semantic type information is assigned until the subsequent AST mapping phase.

#1.1 Token Classification & Consumption Rules

Character Class Handling Behavior Emitted Token
Whitespace (Char.IsWhiteSpace) Silently consumed. Acts as a hard boundary between contiguous atoms. None
Open Parenthesis ( Immediately consumed and pushed to the token accumulator. Denotes the start of a list scope. "("
Close Parenthesis ) Immediately consumed and pushed. Denotes the termination of the current list scope. ")"
Line Comment Start ; Triggers comment consumption. The scanner advances the index past all characters until a newline (\n, \r) or buffer end is encountered. The entire sequence is discarded. None
Atom Characters (any other) The scanner reads a maximal contiguous substring until isTokenSeparator evaluates to true (Char.IsWhiteSpace, (, or )). The substring is pushed as a single lexical unit. "<atom>"

#1.2 Lexical Constraints & Invariants

  • No Implicit Concatenation: Adjacent non-separator characters form a single atom. a+b is tokenized as "a+b", not three tokens. Explicit spacing is mandatory for operator invocation: (+ a b).
  • No String Literals or Floating-Point Notation: The tokenizer recognizes only base-10 integer sequences and symbolic identifiers. Constructs like 3.14, 0xFF, or "text" are treated as variable names (Var).
  • Case & Unicode Sensitivity: Atom extraction preserves exact character casing and supports full Unicode/Cyrillic ranges. Нормалдаки ≠ нормалдаки.
  • Comment Scope: Only single-line comments are supported. Multi-line block comments (/* */) are lexically invalid and will either terminate parsing prematurely or be interpreted as malformed atoms.

#1.3 Literal Resolution Pipeline (atomToExpr)

Atoms are classified into initial AST nodes based on strict string equality and integer parsing:

  1. Integer Check: Int32.TryParse is applied. Success yields Ast.Number.
  2. Boolean Check: Exact match against "нормалдаки" → Ast.Bool true, "плаки_плаки" → Ast.Bool false.
  3. Variable Fallback: Any atom failing the above checks becomes Ast.Var "<name>". No predeclaration or scope validation occurs at this stage.

#2. S-Expression Structure

Following tokenization, the flat token stream is transformed into a hierarchical intermediate representation called SExpr via a recursive descent algorithm (parseSExpressions). This phase enforces structural well-formedness before semantic mapping.

#2.1 Intermediate Representation 

type private SExpr =
| Atom of string
| SList of SExpr list
  • Atom: Terminal node carrying the raw lexical string.
  • SList: Recursive container representing a fully parenthesized group. The list order preserves lexical sequence after post-traversal reversal.

#2.2 Parsing Algorithm & State Transitions

Function Input State Action Output
parseOne Token list head Dispatches based on first token. "(" → enters parseList. ")" → triggers error. atom → returns Atom atom. (SExpr * remainingTokens)
parseList Accumulator + tokens Recursively calls parseOne, prepending results. Stops at ), reverses accumulator to restore lexical order, wraps in SList. (SList * remainingTokens)
parseAll Full token list Repeatedly invokes parseOne until exhaustion. Collects all top-level expressions. SExpr list

#2.3 Structural Guarantees & Failure Modes

  • Strict Parenthesis Balancing: Every ( must have a corresponding ). Unmatched ) triggers "Unexpected closing parenthesis.". Unterminated ( triggers "Missing closing parenthesis." or "Unexpected end of input."
  • Order Preservation: The accumulator uses :: (cons) for O(1) insertion, requiring List.rev upon list closure to maintain correct evaluation order.
  • No Partial Trees: Parsing is all-or-nothing. Any structural violation halts compilation immediately; no partial AST is passed to the evaluator.

#3. Special Forms & Syntactic Keywords

The semantic translation occurs in sexprToExpr, which exhaustively pattern-matches on the head atom of each SList. Match order is critical: specific syntactic forms are evaluated before the generic function-application fallback. Deviations in arity or structure trigger immediate compilation failure.

#3.1 Dispatch Table & AST Mapping

Lexical Form Syntactic Pattern Arity Resulting Ast.Expr Constraints & Notes
Sequence (да_будет_свет expr₁ expr₂ ... [я_помылся]) ≥0 Sequence Evaluates expressions in order. я_помылся is an optional terminator stripped during parsing if it appears as the final element.
Conditional (плаки_плаки_или_нормалдаки cond then else) Exactly 3 If cond must evaluate to a boolean. Both branches are lazily evaluated based on condition outcome.
Local Binding (Strict) (браво_босс name value body) Exactly 3 Let name is bound to the evaluated value and visible only within body.
Global Definition (браво_босс name value) Exactly 2 Define Module-level binding. Evaluated in the current sequence scope.
Recursive Binding (еще_посидим name lambda body) Exactly 3 LetRec name must be a Lambda node. Self-reference is enabled within body.
Global Recursive (еще_посидим name lambda) Exactly 2 DefineRec Registers a self-referential function at the sequence level.
Lazy Binding (еще_посидим_лениво name value body) Exactly 3 LetLazy value is wrapped in a deferred thunk. Evaluation occurs on first access within body.
Global Lazy (еще_посидим_лениво name value) Exactly 2 DefineLazy Creates a deferred global thunk.
Lambda (омайгад (param₁ param₂ ...) body) Exactly 2 Lambda Parameters must be an SList of Atoms. Nested expressions as parameters are rejected.

#3.2 Parsing Rules & Enforcement Mechanics

  1. Strict Arity Validation: Each special form expects a fixed number of arguments. Extra or missing arguments bypass the specific pattern and fall into the generic Call matcher, or trigger runtime arity mismatches.
  2. Terminator Handling Logic: For да_будет_свет, the parser reverses the tail, checks for Atom "я_помылся", and conditionally strips it before mapping the remaining elements to Sequence.
  3. Lambda Parameter Validation: The expectAtom helper ensures parameter lists contain only atomic identifiers. (омайгад (x (+ 1 2)) body) is syntactically invalid.
  4. Keyword Precedence & Fallback: The pattern matcher is ordered from most specific to most general. (да_будет_свет ...) is never interpreted as a function call. Any unrecognized head atom defaults to Call(sexprToExpr func, args), enabling dynamic higher-order invocation.
  5. No Infix or Mixfix Syntax: Operators like +, -, * are lexically identical to identifiers. They only gain operational meaning when resolved as built-in functions during evaluation. Prefix notation is mandatory for all invocations.

#4. Formal Grammar (EBNF)

The following Extended Backus-Naur Form precisely defines MelLang's syntax as implemented in Parser.fs. It captures lexical tokenization rules, S-expression structure, special form arity, and program composition logic. 

(* Top-Level Composition *)
Program       ::= Expression*
Expression    ::= Atom | List
Atom          ::= Integer | Boolean | Identifier
Integer       ::= /[0-9]+/
Boolean       ::= "нормалдаки" | "плаки_плаки"
Identifier    ::= /[^\s();]+/
List          ::= "(" Element* ")"
Element       ::= Expression | Terminator
Terminator    ::= "я_помылся"

(* Special Forms - Matched by head atom in sexprToExpr *)
Sequence      ::= "(" "да_будет_свет" Expression* [Terminator] ")"
Conditional   ::= "(" "плаки_плаки_или_нормалдаки" Expression Expression Expression ")"
LocalBind     ::= "(" "браво_босс" Identifier Expression Expression ")"
GlobalDef     ::= "(" "браво_босс" Identifier Expression ")"
RecLocalBind  ::= "(" "еще_посидим" Identifier Lambda Expression ")"
RecGlobalDef  ::= "(" "еще_посидим" Identifier Lambda ")"
LazyLocalBind ::= "(" "еще_посидим_лениво" Identifier Expression Expression ")"
LazyGlobalDef ::= "(" "еще_посидим_лениво" Identifier Expression ")"
Lambda        ::= "(" "омайгад" ParameterList Expression ")"
ParameterList ::= "(" Identifier* ")"
Print         ::= "(" "скажи_это_сон_да" Expression ")"
Square        ::= "(" "что_за_бизнес" Expression ")"
ExplicitCall  ::= "(" "дай_его" Expression Expression+ ")"
ImplicitCall  ::= "(" Expression Expression* ")"

Grammar Notes:

  • Program consists of zero or more top-level Expression nodes. The parse function automatically wraps multiple top-level forms into a Sequence AST node.
  • Terminator (я_помылся) is lexically valid anywhere but syntactically significant only as the final element of a да_будет_свет list, where it is conditionally stripped during mapping.
  • Lambda requires exactly one Expression as its body. Complex bodies must be wrapped in (да_будет_свет ...) to form a valid Sequence.
  • ExplicitCall and ImplicitCall are syntactically distinct but semantically equivalent; both map to Ast.Call.
  • All operators (+, -, *, /, etc.) are parsed as Identifier atoms and resolved to built-in functions during evaluation. No infix or mixfix notation exists in the grammar.

#5. Parsing Rules & Constraints

The parser enforces strict structural and semantic boundaries before any evaluation occurs. These rules guarantee deterministic AST generation and immediate failure on malformed input.

#5.1 Parenthesis & Structural Integrity

  • Strict Balancing: Every ( must have a corresponding ). The recursive descent algorithm (parseList) maintains an accumulator and consumes tokens until a closing parenthesis is encountered.
  • Fail-Fast Conditions:
    • Unexpected closing parenthesis.: Triggered when ) appears without a preceding (.
    • Missing closing parenthesis.: Triggered when the token stream is exhausted before a list is closed.
    • Unexpected end of input.: Triggered when parseOne receives an empty token list during top-level parsing.
  • Order Preservation: parseList uses :: (cons) for O(1) insertion, requiring List.rev upon closure to restore lexical order. No partial AST is ever passed to the semantic mapper.

#5.2 Ordered Pattern Matching & Keyword Precedence

sexprToExpr applies exhaustive pattern matching on SList heads. Match order is critical:

  1. Specific syntactic forms (да_будет_свет, плаки_плаки_или_нормалдаки, браво_босс, etc.) are matched first.
  2. омайгад requires its second element to be an SList of atoms, validated via expectAtom.
  3. дай_его is matched explicitly before the generic fallback.
  4. Fallback: Any SList not captured by prior rules defaults to SList(functionExpr :: argumentExprs) → Call(...). This enables dynamic higher-order invocation while preventing keyword collisions.

#5.3 Arity Enforcement & Fallback Resolution

  • Each special form expects a fixed list length. Deviations bypass specific patterns and fall into the generic Call matcher or trigger runtime arity mismatches during evaluation.
  • Example: (браво_босс x 10) matches GlobalDef (2 args), while (браво_босс x 10 x) matches LocalBind (3 args). A 4-argument form would fall through to Call and likely fail at runtime due to invalid function invocation.

#5.4 Lambda Parameter Validation

  • Parameters must be atomic identifiers. The helper expectAtom enforces this: 
    let private expectAtom sexpr =
    match sexpr with
    | Atom value -> value
    | _ -> failwith "Expected atom."
  • Nested lists or expressions as parameters (e.g., (омайгад ((x 1)) body)) are rejected at parse time.

#5.5 Block Termination Handling

  • In да_будет_свет, the parser reverses the tail, checks for Atom "я_помылся", and conditionally removes it before mapping remaining elements to Sequence.
  • This allows both (да_будет_свет A B я_помылся) and (да_будет_свет A B) to compile to Sequence [A; B], preserving backward compatibility with optional termination syntax.

#5.6 Error Semantics

  • All parse-time errors are raised via failwith with deterministic messages.
  • Errors propagate immediately to Program.fs, which routes them to stderr with a non-zero exit code.
  • No syntax recovery or error-tolerant parsing is implemented; the compiler prioritizes correctness and academic clarity over developer convenience.

#7. Design Notes & Academic Context

The syntactic and lexical design of MelLang is driven by pedagogical clarity, formal correctness, and adherence to classical language implementation principles.

#7.1 Uniformity & Precedence Elimination

By adopting a fully parenthesized, prefix-only S-expression syntax, MelLang eliminates operator precedence and associativity ambiguities entirely. This aligns with Lisp-family design principles and ensures that parsing reduces to a single structural transformation: matching list heads to semantic actions. The absence of infix notation guarantees that every syntactic construct is unambiguously resolvable via pattern matching on SList length and head atom.

#7.2 Lexical-Semantic Decoupling

The use of culturally derived keywords (да_будет_свет, плаки_плаки_или_нормалдаки, etc.) is a deliberate pedagogical choice. It demonstrates that language keywords are arbitrary tokens bound to fixed operational semantics. The parser does not treat these strings as reserved words; they are parsed as standard Atom nodes and only gain syntactic meaning during the sexprToExpr phase. Replacing the entire keyword set with conventional identifiers (e.g., if, let, lambda) would require only string substitutions in Parser.fs without modifying the tokenizer, AST, or evaluator.

#7.3 Strict Phase Separation

MelLang enforces a classical compiler front-end pipeline:

  1. Lexical Analysis (tokenize): Character → Token stream
  2. Syntactic Analysis (parseSExpressions): Token stream → SExpr tree
  3. Semantic Transformation (sexprToExpr): SExpr → Ast.Expr No phase interleaving occurs. The evaluator (Interpreter.fs) receives only fully typed AST nodes, guaranteeing that syntactic errors are caught before runtime. This separation simplifies debugging, enables independent testing of each phase, and mirrors production compiler architectures.

#7.4 Extensibility & Maintainability

The architecture is highly extensible:

  • Adding a new construct requires only a new Expr case in Ast.fs and a corresponding pattern in sexprToExpr.
  • The tokenizer requires no modification, as it already handles arbitrary Unicode/Cyrillic atoms.
  • Built-in functions are injected via Map.add in Interpreter.fs, requiring no parser changes. This modularity ensures that language evolution does not necessitate architectural refactoring, making the codebase suitable for iterative academic experimentation.

#7.5 Pedagogical & Academic Alignment

MelLang is explicitly designed to demonstrate core concepts in programming language theory and functional interpreter implementation:

  • Recursive Descent Parsing: Implemented via parseOne/parseList/parseAll with explicit accumulator reversal.
  • AST Transformation: Clear mapping from untyped S-expressions to a discriminated union representing computational primitives.
  • Environment-Passing Evaluation: Lexical scoping, closure capture, and recursive binding are implemented via immutable Map structures passed explicitly through the evaluator.
  • Lazy Evaluation Semantics: System.Lazy<T> integration demonstrates call-by-need evaluation with memoization, isolated to the LetLazy/DefineLazy constructs.
  • Error Isolation: Parse-time vs runtime error boundaries are strictly enforced, illustrating compiler phase separation.

The project prioritizes implementation clarity over performance optimizations (e.g., no TCO, no bytecode generation, no persistent data structures). It serves as a reference implementation for academic coursework, demonstrating how functional programming principles, algebraic data types, and explicit environment management combine to form a complete, executable language.

#04. Language Semantics

#4.1 The Evaluation Model (Tree-Walking Execution)

MelLang employs a classical tree-walking interpreter architecture. The execution engine does not compile source code to bytecode, emit an intermediate representation, or apply runtime JIT optimizations. Instead, it directly traverses the abstract syntax tree (Ast.Expr) generated by the parser, evaluating each node recursively until a runtime value (Value) is produced. This design prioritizes semantic clarity, debuggability, and strict adherence to functional evaluation principles.

#Core Execution Pipeline

The interpreter is orchestrated by three mutually recursive functions defined in Interpreter.fs:

  1. eval : Env -> Expr -> Value – The primary dispatch engine. Matches on the structure of Expr and recursively evaluates sub-expressions.
  2. apply : Value -> Value list -> Value – Handles function invocation. Validates arity, constructs call environments, and resumes evaluation within function bodies.
  3. evalSequence : Env -> Expr list -> Value – Manages sequential execution of top-level or block-scoped expressions, processing definitions and returning the final computed value.

Execution begins at the public entry point run, which initializes the interpreter with a pre-populated environment of built-in functions: 

let run (program: Expr) : Value = eval builtins program

#Strict Evaluation Strategy

MelLang operates under a strict (eager) evaluation model by default. When encountering a function call (Call (func, args)), the interpreter evaluates the function expression and all argument expressions before invoking apply: 

| Call(functionExpr, argumentExprs) ->
    let functionValue = eval env functionExpr
    let argumentValues = argumentExprs |> List.map (eval env)
    apply functionValue argumentValues

This call-by-value strategy ensures that side effects and computations occur predictably and in lexical order. The only exception to strict evaluation is the explicit lazy binding construct (LetLazy/DefineLazy), which defers computation until the value is first demanded (detailed in Section 4.2).

#Expression Dispatch & Control Flow

The eval function exhaustively pattern-matches on Ast.Expr. Each constructor maps to a specific evaluation rule:

  • Literals (Number, Bool): Return corresponding IntVal or BoolVal immediately.
  • Variables (Var): Perform environment lookup. If the bound value is a LazyVal, it is automatically forced before return.
  • Conditionals (If): Evaluates the condition expression. Uses expectBool (which forces laziness and validates type) to select either the then or else branch for evaluation. Both branches remain unevaluated until selected.
  • Local Bindings (Let, LetRec, LetLazy): Evaluate the bound expression, extend the environment, and continue evaluation of the body expression in the new scope.
  • Side Effects (Print): Evaluates the inner expression, prints its string representation via printfn, and returns the original value to preserve expression semantics.
  • Sequences (Sequence): Delegates to evalSequence, which iterates through the list of expressions, threading the environment forward.

#Function Application (apply)

When apply receives control, it matches on the runtime function representation:

  1. Built-in Functions (BuiltinVal): Directly invoke the native F# closure. All arguments are forced via forceIfLazy prior to execution to ensure type safety and strict evaluation.
  2. User-Defined Closures (FunctionVal): Validates parameter count against argument count. Constructs a new call environment via bindArguments and evaluates the closure's body within it.
  3. Recursive Functions (RecFunctionVal): Performs the same validation and binding, but explicitly injects the function's self-reference into the call environment before evaluation, enabling direct recursion.

#Sequence Execution (evalSequence)

The evalSequence function implements a tail-recursive loop that processes expressions sequentially:

  • Definitions (Define, DefineRec, DefineLazy): Evaluate or wrap the bound value, extend the current sequence environment, and continue with UnitVal as the intermediate result.
  • General Expressions: Evaluate normally, threading the resulting value forward.
  • Termination: Returns the value of the final evaluated expression. If the sequence is empty, returns UnitVal.

This loop-based approach ensures that top-level definitions accumulate in the environment without creating deep nesting of Let bindings, mirroring module-level scoping in traditional languages.

#4.2 Environment & Scoping (Immutable Lexical Contexts)

MelLang's execution model is fundamentally stateless. All variable bindings, function scopes, and closure contexts are managed through immutable persistent environments, formally typed as: 

type Env = Map<string, Value>

This design guarantees referential transparency, eliminates shared mutable state, and provides deterministic lexical scoping semantics.

#Persistent Environment Model

Environments are never mutated in place. Every binding operation produces a new Map instance that shares structural references with its parent when possible. When eval processes a Let expression, it creates a new environment by extending the current one: 

| Let(name, valueExpr, bodyExpr) ->
    let value = eval env valueExpr
    let newEnv = env.Add(name, value)
    eval newEnv bodyExpr

The original env remains intact, ensuring that nested scopes cannot accidentally overwrite outer bindings. This immutability is critical for correctness in higher-order function patterns and nested lexical blocks.

#Lexical Scoping & Closure Capture

Functions are first-class values that capture their defining environment at creation time. When the interpreter encounters a Lambda node, it constructs a FunctionVal that permanently stores the current Env: 

| Lambda(parameters, body) ->
    FunctionVal(parameters, body, env)

This captured environment (closureEnv) becomes the base context for all future invocations of that function, regardless of where or when it is called. This behavior implements static (lexical) scoping, ensuring that free variables inside a function body resolve to the bindings visible at definition time, not call time.

#Argument Binding & Frame Creation

Function calls create isolated activation frames through the bindArguments helper: 

let private bindArguments (baseEnv: Env) (parameters: string list) (arguments: Value list) : Env =
    List.zip parameters arguments
    |> List.fold (fun currentEnv (name, value) -> currentEnv.Add(name, value)) baseEnv

This function zips formal parameters with evaluated arguments and folds them into a new environment. The resulting callEnv shadows parameter names over the captured closure environment, implementing standard FP argument passing semantics. Since Map.Add overwrites existing keys, parameter names take precedence over any outer bindings with identical identifiers.

#Recursive Self-Reference Mechanics

Recursive functions require special handling because their definition must be visible within their own body. MelLang achieves this without fixed-point combinators by using a dedicated RecFunctionVal constructor: 

| RecFunctionVal of string * string list * Expr * Env

During LetRec evaluation, the interpreter creates this value and adds it to the environment. However, the self-reference is not fully resolved until invocation. Inside apply, when a RecFunctionVal is called, the interpreter explicitly injects the function into its own call environment: 

| RecFunctionVal(functionName, parameters, body, closureEnv) ->
    let self = RecFunctionVal(functionName, parameters, body, closureEnv)
    let callEnv = 
        bindArguments closureEnv parameters argumentValues 
        |> fun currentEnv -> currentEnv.Add(functionName, self)
    eval callEnv body

This delayed self-injection ensures that recursive calls resolve to the same function instance, enabling standard recursive algorithms (factorial, fibonacci, tree traversal) to work naturally.

#Lazy Value Resolution in Environments

The environment interacts directly with MelLang's call-by-need evaluation strategy. When a LetLazy binding is created, the interpreter wraps the unevaluated expression in a .NET Lazy<Value> thunk and stores it as a LazyVal: 

| LetLazy(name, valueExpr, bodyExpr) ->
    let lazyValue = LazyVal(lazy (eval env valueExpr))
    let newEnv = env.Add(name, lazyValue)
    eval newEnv bodyExpr

Crucially, lazy evaluation is transparent to the environment lookup mechanism. When eval resolves a Var, it checks the retrieved value: 

| Var name ->
    match env.TryFind name with
    | Some (LazyVal thunk) -> thunk.Force()
    | Some value -> value
    | None -> failwithf "Unknown variable: %s" name

If the bound value is a LazyVal, the thunk is forced exactly once. Subsequent lookups of the same variable retrieve the cached result, providing automatic memoization. This design decouples lazy evaluation semantics from the binding mechanism, allowing lazy values to flow through closures, higher-order functions, and sequence definitions without special-case handling in bindArguments or apply.

#Sequence-Level vs. Expression-Level Bindings

MelLang distinguishes between two binding lifecycles based on syntactic context:

  • Expression-Level (Let, LetRec, LetLazy): Creates a new lexical scope for a single body expression. The binding is local to that expression and disappears once evaluation exits the scope.
  • Sequence-Level (Define, DefineRec, DefineLazy): Mutates the iterative environment within evalSequence. These bindings persist for all subsequent expressions in the block, effectively simulating module-level declarations. The loop maintains a single currentEnv that is extended with each definition, allowing later expressions to reference earlier declarations without nested Let structures.

This dual-binding model provides both the compositional safety of expression-local scoping and the practical convenience of sequential program construction, while strictly preserving immutability and lexical correctness throughout execution.

#3. Lazy Evaluation Mechanics

MelLang implements explicit, memoized call-by-need semantics through the LazyVal runtime constructor and the System.Lazy<T> .NET primitive. Unlike strict bindings, lazy expressions are not evaluated during environment construction. Instead, they are wrapped in a deferred computation thunk that remains dormant until its value is explicitly demanded.

#3.1 Thunk Creation & Binding

When the interpreter encounters a LetLazy or DefineLazy node, it does not call eval on the bound expression immediately. Instead, it captures the current lexical environment and wraps the evaluation call inside a lazy thunk: 

| LetLazy(name, valueExpr, bodyExpr) ->
    let lazyValue = LazyVal(lazy (eval env valueExpr))
    let newEnv = env.Add(name, lazyValue)
    eval newEnv bodyExpr

The resulting LazyVal is stored directly in the environment map. This guarantees that the closure's dependencies are captured at definition time, but execution is deferred until runtime demand.

#3.2 Transparent Forcing & Memoization

Lazy evaluation in MelLang is entirely transparent to the programmer. The interpreter automatically forces thunks during variable resolution: 

| Var name ->
    match env.TryFind name with
    | Some (LazyVal thunk) -> thunk.Force()
    | Some value -> value
    | None -> failwithf "Unknown variable: %s" name

When a lazy variable is referenced, thunk.Force() triggers the captured eval computation. Crucially, System.Lazy<T> provides built-in thread-safe memoization: the first access computes and caches the result, while all subsequent lookups return the cached Value without re-evaluation. This prevents redundant computation in recursive or heavily reused lazy bindings.

#3.3 Forced Evaluation in Built-ins & Control Flow

To maintain type safety and predictable control flow, all built-in operations and conditional checks explicitly force lazy values before pattern matching. The forceIfLazy helper normalizes runtime values: 

let private forceIfLazy (value: Value) : Value =
    match value with
    | LazyVal thunk -> thunk.Force()
    | _ -> value

Functions like binaryInt, binaryCompare, and expectBool apply forceIfLazy across their argument lists prior to validation. This ensures that lazy integers participate correctly in arithmetic, lazy booleans drive conditional branching, and lazy lists feed into higher-order operations without triggering runtime type mismatches.

#4. Function Application & Recursion

Function invocation in MelLang is managed by the apply dispatcher, which bridges the gap between closure representation and lexical evaluation. The interpreter supports both standard closures and explicitly recursive functions through distinct Value constructors.

#4.1 Closure Capture & Argument Binding

User-defined functions are represented as FunctionVal, capturing three components: parameter names, body expression, and the defining environment: 

| Lambda(parameters, body) ->
    FunctionVal(parameters, body, env)

Upon invocation, apply first validates arity. A mismatch immediately raises a runtime error, enforcing strict contract compliance: 

if parameters.Length <> argumentValues.Length then
    failwithf "Function expected %d arguments, but got %d." parameters.Length argumentValues.Length

Arguments are then bound to parameters via bindArguments, which zips formal names with evaluated values and folds them into a new environment layer: 

let private bindArguments (baseEnv: Env) (parameters: string list) (arguments: Value list) : Env =
    List.zip parameters arguments
    |> List.fold (fun (currentEnv: Env) (name, value) -> currentEnv.Add(name, value)) baseEnv

The resulting callEnv shadows outer bindings, implementing standard lexical scoping. The function body is then evaluated within this isolated activation frame.

#4.2 Recursive Self-Reference Injection

Standard closures cannot reference themselves because their name is not bound within their own body. MelLang solves this via RecFunctionVal, which stores the function's identifier alongside its captured context: 

type Value =
| ...
| RecFunctionVal of string * string list * Expr * Env

During LetRec evaluation, the interpreter constructs this value and binds it to the specified name. When apply receives a RecFunctionVal, it dynamically injects a self-reference into the call environment before body evaluation: 

| RecFunctionVal(functionName, parameters, body, closureEnv) ->
    let self = RecFunctionVal(functionName, parameters, body, closureEnv)
    let callEnv = 
        bindArguments closureEnv parameters argumentValues 
        |> fun currentEnv -> currentEnv.Add(functionName, self)
    eval callEnv body

This delayed injection ensures that recursive calls resolve to the exact same function instance, enabling direct self-reference without fixed-point combinators or global state mutation. The same mechanism applies to top-level DefineRec declarations within evalSequence.

#4.3 Higher-Order & Partial Application

Built-in higher-order functions (думала_думала, танцуем_все, парни_прикиньте) leverage curried-style pattern matching to support partial application. If fewer arguments than required are provided, they return a new BuiltinVal that closes over the supplied arguments: 

let rec private builtinMap (values: Value list) : Value =
    match values |> List.map forceIfLazy with
    | [functionValue; ListVal items] -> 
        items |> List.map (fun item -> apply functionValue [item]) |> ListVal
    | [functionValue] -> 
        BuiltinVal(fun moreValues -> builtinMap (functionValue :: moreValues))
    | _ -> failwith "думала_думала expects a function and a list."

This design enables seamless composition with the pipeline operator (бем_бем_бем) and preserves functional idioms without requiring explicit currying syntax at the language level.

#6. Error Handling & Side Effects

MelLang enforces a strict separation between pure computation and observable effects. Side effects are confined to a single construct, while error propagation follows a fail-fast exception model.

#6.1 Isolated Side Effects via Print

The only mechanism for observable I/O is the Print AST node, lexically invoked as (скажи_это_сон_да expr). During evaluation, the interpreter computes the inner expression, converts it to a string representation, prints it to standard output, and returns the original value to preserve expression semantics: 

| Print expr ->
    let value = eval env expr
    printfn "%s" (valueToString value)
    value

The valueToString function recursively serializes runtime values:

  • Integers and booleans convert directly ("нормалдаки" / "плаки_плаки").
  • Lists render as comma-separated bracketed sequences.
  • Functions, built-ins, and recursive closures display as opaque placeholders ("<function>", "<builtin>").
  • Lazy values are automatically forced during stringification, ensuring accurate output representation.

#6.2 Dynamic Type Contracts & Validation

MelLang employs a dynamically typed runtime with strict structural validation at operation boundaries. Type mismatches are caught during built-in dispatch rather than at compile time. For example, binaryInt enforces integer-only arithmetic: 

let private binaryInt (name: string) (operation: int -> int -> int) (values: Value list) : Value =
    match values |> List.map forceIfLazy with
    | [IntVal left; IntVal right] -> IntVal(operation left right)
    | _ -> failwithf "Builtin '%s' expects exactly two integer arguments." name

Similarly, expectBool guarantees that conditional branches evaluate to valid boolean values. These contracts prevent silent type coercion and ensure predictable failure semantics when invalid data flows through the evaluation pipeline.

#6.3 Fail-Fast Error Propagation

The interpreter does not implement runtime error recovery, try/catch constructs, or error-return types. All violations trigger F# failwith or failwithf exceptions, which propagate immediately up the call stack. The CLI entry point (Program.fs) intercepts these exceptions, formats them with an Error: prefix, routes them to stderr, and terminates with a non-zero exit code: 

with ex ->
    eprintfn "Error: %s" ex.Message
    1

Common failure categories include:

  • Unknown Variables: Unbound identifiers in Var resolution.
  • Type Mismatches: Passing non-integers to arithmetic, non-booleans to conditionals, or non-lists to sequence operations.
  • Arity Violations: Mismatched parameter/argument counts in user or built-in function calls.
  • Structural Constraints: Empty list access in яблоко_одно, invalid lambda parameters, or malformed recursive definitions.

This fail-fast model prioritizes debugging clarity and academic correctness over fault tolerance, aligning with classical interpreter design principles.

#07. Architecture Guide

This chapter provides a comprehensive technical walkthrough of the MelLang interpreter's internal architecture. It details module responsibilities, data flow, environment management, lazy execution mechanics, and extensibility patterns. The guide is intended for contributors, reviewers, and advanced users who need to understand how the interpreter operates at the implementation level.

#7.1 Module Responsibilities & Compilation Pipeline

MelLang is structured as a strictly layered, single-pass interpreter written in F#. Due to F#'s requirement for explicit dependency ordering, the project file (MelLang.fsproj) enforces a rigid compilation sequence: 

<Compile Include="Ast.fs" />
<Compile Include="Parser.fs" />
<Compile Include="Interpreter.fs" />
<Compile Include="Program.fs" />
Module Responsibility Key Types & Functions
Ast.fs Defines the core algebraic data types. Separates static syntax from runtime representation. Expr (AST nodes), Value (runtime values), Env = Map<string, Value>
Parser.fs Lexical analysis, S-expression construction, and AST mapping. Strictly pure; no runtime state. tokenize, parseSExpressions, sexprToExpr, parse
Interpreter.fs Tree-walking evaluation, environment threading, lazy forcing, and built-in registry. eval, apply, evalSequence, forceIfLazy, builtins, run
Program.fs CLI entry point, file I/O, exception routing, and exit code management. main, File.ReadAllText, eprintfn

Design Principle: Each module consumes output from the previous layer and never bypasses it. The parser never sees Values; the evaluator never sees raw strings. This strict phase separation simplifies testing, debugging, and formal verification.

#7.2 Data Flow & Execution Lifecycle

A MelLang program undergoes a deterministic four-stage transformation:

  1. Lexical Analysis (tokenize): Raw source text is scanned character-by-character. Comments (;...) are stripped, whitespace is consumed, and contiguous non-separator characters become atoms. Output: string list.
  2. Syntactic Analysis (parseSExpressions): Tokens are transformed into a hierarchical intermediate representation (SExpr). Parentheses define list boundaries. Output: SExpr list.
  3. Semantic Mapping (sexprToExpr): SExpr nodes are matched against keyword patterns and converted to strongly-typed Ast.Expr nodes. Output: Expr.
  4. Evaluation (Interpreter.run): The AST is traversed by eval, starting with an environment pre-populated with built-in functions. Output: Value.

The public API parse : string -> Expr orchestrates stages 1–3, automatically wrapping multiple top-level expressions into a Sequence node if necessary. Interpreter.run then passes the resulting Expr to eval builtins.

#7.3 Environment Threading & Scoping Mechanics

MelLang implements lexical scoping through explicit, immutable environment passing. There is no global state, implicit stacks, or mutable variable slots.

#Persistent Environment Model 

type Env = Map<string, Value>

Every binding operation produces a new Map instance. The original environment remains unchanged, guaranteeing referential transparency and preventing accidental shadowing across scopes.

#Scope Creation Patterns

Construct Environment Behavior
Let Evaluates valueExpr in current env, extends via env.Add(name, value), evaluates bodyExpr in new scope.
LetRec Validates that valueExpr is a Lambda, constructs RecFunctionVal, binds it, then evaluates body.
LetLazy Wraps eval env valueExpr inside Lazy<Value>, binds as LazyVal, defers evaluation until force.
Sequence / evalSequence Iterates through expressions with a tail-recursive loop. Define/DefineRec/DefineLazy extend the loop's currentEnv without nesting.

#Closure Capture & Recursive Self-Reference

User-defined functions capture their defining environment at creation time: 

FunctionVal(parameters, body, closureEnv)

When invoked, apply constructs a new call environment via bindArguments, which zips formal parameters with evaluated arguments and folds them over closureEnv. This shadows outer bindings while preserving lexical correctness.

Recursive functions use RecFunctionVal(name, parameters, body, closureEnv). During invocation, apply explicitly injects the function into its own call environment: 

let self = RecFunctionVal(...)
let callEnv = bindArguments closureEnv parameters args |> .Add(name, self)

This delayed self-injection enables direct recursion without fixed-point combinators or global symbol tables.

#7.4 Lazy Evaluation & Thunk Management

MelLang implements explicit call-by-need semantics using .NET's System.Lazy<T> for memoization and thread-safe execution.

#Thunk Creation 

| LetLazy(name, valueExpr, bodyExpr) ->
    let lazyValue = LazyVal(lazy (eval env valueExpr))
    let newEnv = env.Add(name, lazyValue)
    eval newEnv bodyExpr

The current lexical environment is captured at binding time. The expression remains completely inert until demanded.

#Transparent Forcing

Lazy evaluation is seamlessly integrated into the evaluation pipeline via forceIfLazy: 

let private forceIfLazy (value: Value) : Value =
    match value with
    | LazyVal thunk -> thunk.Force()
    | _ -> value

This helper is applied universally before:

  • Arithmetic operations (binaryInt, binaryCompare)
  • Conditional evaluation (expectBool)
  • List construction & HOF application
  • Variable resolution (Var case in eval automatically forces LazyVal via thunk.Force())

Once forced, the result is cached. Subsequent accesses return the memoized Value without re-evaluation, guaranteeing at-most-once semantics even in recursive or heavily shared lazy graphs.

#7.5 Built-in Registry & Dynamic Dispatch

Built-in functions are registered in a dedicated Env map and dispatched at runtime via pattern matching.

#Registry Initialization 

let builtins : Env =
    Map.empty<string, Value>
    |> Map.add "+" (BuiltinVal(binaryInt "+" (+)))
    |> Map.add "думала_думала" (BuiltinVal builtinMap)
    // ...

Each entry adheres to the Value list -> Value signature. Arity and type contracts are enforced dynamically via pattern matching on values |> List.map forceIfLazy.

#Partial Application Support

Higher-order builtins (map, filter, fold) support currying by returning a new BuiltinVal when insufficient arguments are provided: 

| [functionValue] -> BuiltinVal(fun moreValues -> builtinMap (functionValue :: moreValues))

This enables seamless integration with the pipeline operator (бем_бем_бем) and declarative composition patterns.

#Dispatch in apply 

match forceIfLazy functionValue with
| BuiltinVal builtin -> builtin argumentValues
| FunctionVal(...) -> ...
| RecFunctionVal(...) -> ...
| _ -> failwith "Trying to call a non-function value."

Lazy function references are automatically forced before dispatch, ensuring compatibility with lazy-bound higher-order functions.

#7.6 Error Isolation & Runtime Contracts

MelLang employs a fail-fast exception model with strict phase boundaries.

Error Category Trigger Location Message Format Exit Behavior
Lexical/Syntactic Parser.fs "Unexpected end of input.", "Missing closing parenthesis." Immediate termination via failwith
Unbound Identifier Interpreter.eval (Var case) "Unknown variable: <name>" Exception propagated to CLI
Type Mismatch binaryInt, binaryCompare, expectBool "Builtin '<op>' expects exactly two integer arguments." Runtime failwithf
Arity Violation Interpreter.apply "Function expected N arguments, but got M." Runtime failwithf

Error Routing (Program.fs):

with ex ->
    eprintfn "Error: %s" ex.Message
    1

All exceptions bypass normal execution, route to stderr, and terminate with a non-zero exit code. MelLang source code has no try/catch construct; errors are intended to be fatal and debuggable.

#7.7 Extensibility & Contribution Guidelines

The architecture is highly modular, enabling safe extension without refactoring core evaluation logic.

#Adding a Built-in Function

  1. Define a function matching Value list -> Value in Interpreter.fs.
  2. Apply forceIfLazy to all arguments before pattern matching.
  3. Register via |> Map.add "<name>" (BuiltinVal <func>) in the builtins pipeline.
  4. No parser or AST changes required.

#Adding a New Syntactic Construct

  1. Add a case to Ast.Expr (e.g., | Loop of Expr * Expr * Expr).
  2. Add a pattern to Parser.sexprToExpr mapping the keyword to the new AST node.
  3. Implement evaluation logic in Interpreter.eval (and apply if it introduces new values).
  4. Ensure forceIfLazy is applied where type contracts are enforced.

#Modifying Evaluation Semantics

  • Extend eval/apply pattern matching. Maintain explicit env threading.
  • Avoid mutable state. Use immutable data structures and persistent collections.
  • Preserve phase separation: parsing logic must not depend on runtime values.

#Testing & Validation

  • Place .mel files in examples/.
  • Run via dotnet run -- examples/<file>.mel.
  • Verify exit code 0 for success, 1 for expected failures.
  • Compare stdout against documented expectations.

#7.8 Architectural Trade-offs & Design Decisions

Decision Rationale Trade-off
Tree-Walking Interpreter Maximizes code readability, simplifies debugging, aligns with academic FP coursework. No TCO, no bytecode optimization, higher memory/CPU overhead for deep recursion.
Explicit Env Threading Demonstrates lexical scoping, closure capture, and persistent environments clearly. Map lookup/insertion overhead vs. implicit stack frames.
Dynamic Typing with Runtime Contracts Eliminates compile-time type inference complexity, allows flexible HOF patterns. Type errors surface at runtime, not parse time. Requires thorough example coverage.
.NET Lazy<T> for Thunks Leverages platform-native memoization, thread-safety, and at-most-once semantics. Couples interpreter to .NET runtime; not portable to non-CLI targets without reimplementation.
Fail-Fast Error Model Guarantees deterministic failure, simplifies debugging, aligns with pure FP principles. No graceful degradation or error recovery in source programs.

MelLang prioritizes semantic clarity, academic rigor, and educational demonstrability over production-grade performance. Every architectural choice reinforces the project's core mission: proving that functional programming concepts, explicit environment management, and lazy evaluation can be implemented transparently, correctly, and extensibly within a minimal codebase.
